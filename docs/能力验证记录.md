### 结论评级

**A（可用级）**：从一句需求文档出发，一次会话内产出一个可安装、可开源、有测试、真实数据可跑的插件。需求中的四个模块全部交付，P0 全部达成且超出验收线（分类 100% vs 70%）。

**平台能力边界（本次未卡住）**：
- `ctx.webServer.register({kind:"prefix"})` 足够支撑一整套 REST 接口；
- `ctx.tools.register()` 的工具定义形状清晰，8 个工具一次注册成功；
- `ctx.slots.register()` 的 `main`(keyed) + `sidebar.panellist`(list) 组合足以承载多页面板；
- `ctx.llm.stream()` + `agentDefaultModel` 让「用用户自己的模型」变得直接。

**本次真正卡住的是模型能力而非平台**：
1. 一次机械正则改写把组件文件改脏，产生 1452 行重复块与语法错误——**模型在「批量改写大文件」上不可靠**，应先 `node --check` 再继续；
2. 离线测试替身的 hook 时序多次误判，需要反复收敛——**模型对自己产出的测试基建缺乏正确心智模型**；
3. 契约先行（`CONTRACT.md`）显著减少了跨模块返工，但**接口签名仍需 Lead 反复核对**。

## 五、卡点复盘（对「灵基 Build 开发能力」的直接启发）

| 卡点 | 现象 | 根因 | 可复用做法 |
|---|---|---|---|
| 大文件批量改写 | 正则替换把正确的 `jsx` 调用改坏，产生重复块 | 模型不擅长跨语义边界的机械改写 | 每次机械改写后立即 `--check`；更好的做法是**逐处 edit 而非全局正则** |
| 并发写同一文件 | 构建产物一度被截断 | 构建与源码编辑并发 | 构建产物由单一角色生成，且只在源码稳定后跑 |
| 契约漂移 | 前后端对 `store` 方法签名认知不一致 | 多角色并行 | **先写 `CONTRACT.md`，再并行开发**，签名锁定后不允许随意改 |
| 方向列识别遗漏 | 通用银行流水 `收支方向` 列未识别，收入被记成支出 | 别名表不全 | 用真实导出格式做验收，而非自造样例；**边界值要穷举** |
| 测试替身与真 React 不一致 | 面板 8 条测试失败，但功能是对的 | 自建最小 React 替身不模拟 setState 时序 | 离线测试要明确「测的是逻辑还是渲染」；真机验证不可省 |

## 五·补：第二轮迭代（默认数据与「随手记」）

第一版能跑通链路，但第一次打开是空的、记账要填表——这不符合「个人工作台」的实际使用方式。第二轮针对性补了两块：

### 1. 开箱即有数据的演示账本

| 项目 | 第一版 | 现版本 |
|---|---|---|
| 数据量 | 108 笔 / 6 个月 | **1,124 笔 / 12 个月** |
| 生成方式 | 每月 16 条模板轮转 | 按日历生成：工作日通勤+外卖、周末聚餐+电影、每月房租水电，叠加旅行月/换电脑/体检/婚礼/双十一/年货/换季 |
| 资产 | 4 项 | 6 项（含微信零钱、货币基金） |
| 持仓 | 4 项（全赚） | 5 项（**有赚有亏**，更真实） |
| 首开体验 | 空状态两个按钮 | 自动铺好 + 顶部「这是演示账本」提示条 + 一键清空 |
| 当月数据薄 | — | 自动落在最近一个完整月份，不当月只有几天就显示当月 |

一致性保护：`demoOffered` 标记保证演示数据**只送一次**，用户清空后不会每次重开又复活。

### 2. 「随手记一笔」常驻输入条

一句话记账：`35 咖啡` / `昨天打车 42` / `发工资 28600` / `11-05 超市 128.5`。
实时预览解析出的金额·商户·日期，认不出金额就原地提示而不写错账，分类交给规则引擎。
新增 5 条面板测试覆盖解析、收入方向、日期偏移、拒绝非法输入、演示清空。

### 本轮修掉的真 bug

- **还款金额显示 ¥0**：`finance_net_worth` 读 `item.monthlyPayment`，而 `analysis.js` 的 `upcoming` 项暴露的是 `amount`。已修复并加回归断言。
- **清空演示数据后自动复活**：初版用 `imports` 里有无 `imp_demo` 判断，清空后该标记也消失，导致重新铺数据。改为持久的 `demoOffered`。
- **当月没有收入**：演示数据发薪日固定 10 号，月初打开时当月收入为 0，结余被房租拉成大负数。改为当月未到发薪日则记在月初。
